# PC Telemetry v1.0 — Codex 开发总引导词

## 一、你的角色与任务

你是一名资深 Android、Windows 桌面应用、实时数据通信和 UI/UX 工程师。

请开发一个名为 **PC Telemetry** 的完整跨设备性能监控系统。

该系统由两个应用组成：

1. Windows Collector：负责读取 Windows 电脑的硬件性能数据，通过局域网发送给 Android。
2. Android Dashboard：将 Android 手机作为独立的横屏 PC 性能仪表盘，展示实时数据。

项目必须交付真实可运行的软件，而不是仅包含界面示例的 Demo。

**重要：采用分阶段开发。每完成一个阶段，必须提供实现总结、测试结果、已知问题和下一阶段计划。未经用户确认，不要擅自进入下一阶段。**

不要虚构测试结果、构建产物或硬件兼容性。

## 二、目标设备与技术要求

### Android

- 最低版本：Android 10（API 29）
- 主要测试设备：小米 8
- 测试设备系统：基于 Android 14 的第三方 HyperOS 2
- 主要横屏分辨率：2248 × 1080
- 主要比例：约 18.7:9
- 同时适配其他常见横屏比例
- 使用 Kotlin + Jetpack Compose
- 自定义仪表优先采用 Compose Canvas
- 使用 Android DataStore 保存设置
- 使用 Android Keystore 保护配对凭据
- 使用前台常亮和沉浸式横屏显示
- 不要求后台持续运行

### Windows

- 支持 Windows 10 / 11 x64
- 使用 C# / .NET 8
- 采用 LibreHardwareMonitor 作为优先传感器方案
- 使用 WinForms NotifyIcon 实现系统托盘
- 采用自包含发布，用户无需额外安装 .NET Runtime
- 支持开机自启
- 普通权限优先，必要时提示管理员权限
- 使用 DPAPI 保护长期配对凭据
- 不依赖 MSI 安装程序
- 允许以便携式文件夹形式运行

## 三、核心监控功能

必须实现六项指标：

| 指标 | 定义 |
|---|---|
| CPU Usage | 整颗 CPU 总使用率 |
| GPU Usage | 当前选中 GPU 的核心使用率 |
| RAM Usage | 已使用物理内存 / 总物理内存 |
| VRAM Usage | 已使用专用显存 / 专用显存总容量 |
| CPU Temperature | CPU Package 温度优先 |
| GPU Temperature | GPU Core 温度优先 |

额外要求：

- Windows 默认每秒采集一次。
- GPU 默认选择独立显卡，允许手动切换。
- 支持 Intel、AMD CPU，以及 NVIDIA、AMD、Intel GPU。
- 对传感器名称建立优先级与回退映射。
- 不可用的数据必须显示 N/A，不允许伪造为 0。
- RAM 和 VRAM 同时提供已使用容量与总容量。
- 区分独立显存与共享系统内存。
- Android 通过动画插值平滑更新读数。
- 不增加 FPS、功耗、风扇转速等额外监控功能。

## 四、Windows 低开销要求（P0）

本项目必须尽量避免影响游戏性能。

建议优化目标：

- 常驻平均 CPU 占用：≤1%（整机总 CPU 百分比口径）
- 稳定运行工作集：≤80 MB
- 默认采集频率：1 Hz
- 游戏平均 FPS 影响目标：≤1%
- 尽量避免影响 1% Low FPS 和帧时间稳定性

这些是优化目标，不能在没有测试的情况下宣称已经达到。

实现要求：

1. 启动时枚举传感器，运行时复用映射。
2. 避免每秒重新扫描全部硬件。
3. 避免重复调用昂贵的硬件更新接口。
4. 采集在后台异步执行，不阻塞托盘 UI。
5. 不使用忙等待、高频轮询或无意义的定时任务。
6. 不创建额外 GPU 3D 渲染上下文。
7. 网络发送每秒合并为一个数据快照。
8. 正常运行不持续写入高频日志。
9. 对传感器采集耗时进行性能测量。
10. 某个传感器异常或过慢时允许降频、隔离和恢复，不得拖慢整个系统。
11. 采集任务不得无控制地并发重入。
12. 程序退出时正确释放硬件监控和网络资源。

请特别注意：LibreHardwareMonitor 的部分 Update 调用可能刷新整组传感器，不能假设读取单个值一定是低开销操作。

性能优化必须基于实测，而不是凭代码结构推断。

## 五、通信与配对

使用局域网 WebSocket 进行实时通信。

要求：

- Windows 作为服务端。
- Android 作为客户端。
- 自动发现局域网内的 Windows Collector。
- 优先考虑 mDNS。
- 必须支持手动输入 IP 和端口。
- 首次连接使用一次性配对码。
- 配对成功后保存长期随机认证凭据。
- 之后自动认证与重连。
- 仅支持一台 Windows 电脑作为当前数据源。
- 不需要云服务或互联网连接。
- 不开放远程命令执行能力。

配对必须有合理的安全设计。不要直接把短配对码当成长期密钥，也不要把长期凭据明文写入配置文件。

如果采用明文 WebSocket，需要明确其安全边界，并设计能够避免长期凭据被直接窃取的认证机制。优先选择成熟的加密通信或安全密钥协商方案，避免自行发明密码学协议。

### 连接状态

至少包含：

- DISCOVERING
- PAIRING
- CONNECTED
- OFFLINE
- RECONNECTING

连续 5 秒未收到有效数据时，进入 OFFLINE。

离线时：

- 保留最后一次有效读数。
- 明确显示 OFFLINE。
- 显示数据距上次更新的时间。
- 自动尝试重连。
- 恢复后平滑更新数据。
- 不得把旧数据当作实时数据。

### 数据协议

建立明确的版本化 JSON 协议。

至少包含：

- 协议版本
- 设备标识
- 数据序列号
- 采集时间
- 六项指标
- RAM/VRAM 容量
- 当前 GPU 信息
- 各传感器可用性
- 数据有效性或时间戳

协议必须提供示例和自动化测试。

## 六、Android 应用基本行为

- 首次启动进入连接与配对向导。
- 已配对设备自动连接。
- 启动后恢复上次使用的主题。
- 强制横屏。
- 前台仪表页面保持屏幕常亮。
- 支持简体中文和英文切换。
- 左右滑动切换 SPORT / HUD。
- 右上角设置按钮打开半透明设置浮层。
- 长按屏幕也可以打开设置。
- 支持系统亮度和夜间暗色模式。
- 支持轻微像素微移，降低 OLED 烧屏风险。
- 不在网络断开时自动展示伪造的模拟数据。

必须提供独立的开发演示模式，以便在没有 Windows 电脑时调试界面。

演示模式必须明确标识为 DEMO，不得与真实监控混淆。

## 七、SPORT 主题设计

### 视觉基准

参考保时捷 911 GT3（992.2）的数字仪表设计语言。

采用已经确认的 **GT3 风格 CPU/GPU 双主表方案**。

核心风格：

- 深黑背景
- 银白机械刻度
- 金属仪表边框
- 红色指针
- 红色高负载刻度区域
- 细腻的碳纤维质感
- 顶部 GT3 风格负载提示灯
- 克制的 ROG 眼睛标识

### 布局

左侧大型圆形仪表：

- CPU Usage
- CPU Temperature

右侧大型圆形仪表：

- GPU Usage
- GPU Temperature

底部：

- RAM 使用率、已使用容量、总容量
- VRAM 使用率、已使用容量、总容量

顶部：

- PC TELEMETRY 标题
- ROG 标识
- SPORT 标识
- 分段式负载提示灯

### 视觉要求

- 仪表指针必须与实际数值严格对应。
- 刻度范围为 0–100%。
- 数字、指针、刻度不能出现数据不一致。
- 动画必须平滑，不能瞬间跳变。
- 不重复显示 CPU/GPU 使用率和温度。
- SPORT 不展示 60 秒趋势曲线。
- 避免大量重复图标和无意义装饰。

不得把整张仪表盘作为静态背景图片使用。必须将指针、数字、刻度、灯带等实现为可动态更新的原生 UI。

ROG 标识应作为可替换的独立素材，并提供不含第三方商标的替代方案。不要暗示软件获得华硕或保时捷官方授权。

## 八、HUD 主题设计

### 视觉基准

采用已确认的第三版 HUD 样稿。

设计方向是**科幻航天器航电终端**，而不是 SPORT 的蓝色皮肤。

核心风格：

- 深蓝黑背景
- 青绿色细线
- 少量橙色强调
- 精密网格与坐标刻度
- 航电终端风格的等宽数字
- 轻微扫描效果
- 适量地球弧线、星空和轨道元素
- 极少量 ROG 品牌元素

### 布局

左侧：

- CPU 使用率
- GPU 使用率
- 直线刻度与分段负载条

中央：

- 最近 60 秒 CPU/GPU 使用率双曲线
- CPU 青色
- GPU 橙色
- 清晰的 0–100% 纵轴
- -60s 到 Now 横轴

右侧：

- CPU/GPU 温度
- RAM 使用率与容量
- VRAM 使用率与容量

底部：

- ONLINE/OFFLINE
- 数据刷新状态
- 必要的连接信息

### 视觉要求

- 不使用 SPORT 风格的圆形机械仪表。
- 避免重复圆角卡片。
- 不重复展示同一指标。
- 不显示虚假的坐标、延迟或运行时间。
- 地球弧线等场景元素仅作轻量背景装饰。
- 图表数据必须来自真实的 60 秒循环缓冲区。
- 断线时停止新增真实数据，明确显示过期状态。
- 优先使用轻量静态素材与 Canvas 绘制，不引入实时 3D 引擎。

## 九、动画与性能

Android 的 UI 动画与 Windows 采集频率必须解耦。

- Windows 数据更新为 1 Hz。
- Android 动画按照实际显示刷新节奏渲染。
- 使用合理的缓动插值。
- 避免每帧重新分配大量对象。
- 避免不必要的全屏重绘。
- 60 秒历史数据使用固定容量循环缓冲区。
- 支持 1–2 秒启动自检动画。
- 低性能设备上允许降低装饰动画复杂度。
- 优先保证数字可读性和操作响应。

有两个重点需要留意：

**第一，Windows 性能目标是优化指标，不是无条件承诺。** 尤其是游戏 FPS 下降不超过 1%，需要通过真实硬件和可重复的游戏场景测试验证。

**第二，阶段 0 必须停下来等待你的确认。** 后续每个阶段同样如此，这样可以及时纠正架构或视觉上的偏差，避免一次性生成大量难以维护的代码。

目前这份引导词已经可以用于启动 PC Telemetry v1.0 的开发。
